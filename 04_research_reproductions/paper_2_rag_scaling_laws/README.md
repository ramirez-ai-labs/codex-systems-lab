# Paper Reproduction: RAG Scaling Laws (Recall & Answer Accuracy vs. k)

## 📄 What This Experiment Is About

This folder reproduces a **pattern discussed in RAG and long-context
research**:

> **Retrieval recall improves with k (chunks retrieved), but with diminishing
> returns, and a bigger corpus needs a bigger k. Downstream answer accuracy
> does not keep climbing with k — past some point, adding more retrieved
> context adds more noise than signal.**

This experiment helps answer:
- Why "just retrieve more chunks" isn't a free lunch
- How corpus size changes the k you need for good recall
- Why RAG systems often cap k well below "retrieve everything"

---

## 🧠 Key Concepts (Beginner-Friendly)

### What is *Recall@k*?

Recall@k is the fraction of queries where the truly relevant document ends
up **somewhere in the top k retrieved results**.

Examples:
- Relevant doc ranked #1, k=5 → **hit**, counts toward recall@5
- Relevant doc ranked #37, k=5 → **miss**
- 200 queries, 130 hits at k=10 → recall@10 = **65%**

---

### What is *Context Dilution*?

Even when the relevant chunk *is* retrieved, a downstream LLM has to find it
among `k - 1` other, irrelevant chunks. As k grows, that gets harder —
sometimes called "lost in the middle" in long-context literature. This means
downstream answer accuracy can **fall even as recall keeps rising**.

---

## 🔬 What This Reproduction Demonstrates

We recreate the relationship:

| k | Recall | Downstream Accuracy |
|---|--------|---------------------|
| Small (1–5) | Low–medium | Low–medium, rising |
| Medium (10–20) | High | **Peaks here** |
| Large (50–100) | Very high | Falls off |

And separately, how a bigger corpus shifts recall down at every k:

| Corpus Size | Recall@10 |
|---|---|
| 100 docs | 79.0% |
| 1,000 docs | 36.5% |
| 10,000 docs | 7.0% |

This mirrors real findings from:
- RAG scaling-law discussions (recall vs. retrieved-set size)
- Long-context "lost in the middle" research
- Production RAG systems capping k rather than maximizing it

## 📓 `replicate_experiment.ipynb`

**Status: implemented and executed.** Run it yourself with:

```bash
jupyter nbconvert --to notebook --execute --inplace replicate_experiment.ipynb
```

The notebook walks through:

1. Generating synthetic query/document embeddings (random unit vectors, 32
   dimensions) across three corpus sizes (100, 1,000, 10,000 documents), with
   exactly one truly relevant document per query
2. Measuring the actual **rank of the relevant document** via cosine
   similarity, and computing **Recall@k** for k = 1, 2, 3, 5, 10, 20, 50, 100
3. Defining a hand-picked **context-dilution function** that converts k into
   a probability, then sampling a real accept/reject outcome per query (fixed
   seed = 42) to get a simulated **answer accuracy@k**
4. Visualizing both curves side by side, across all three corpus sizes

Everything is:

- Small (200 synthetic queries per corpus size, runs in seconds)
- CPU-friendly, no GPU, no external API calls, no real embedding model
- Heavily commented
- Designed for learning, not scale

`RESULTS.md` in this folder reports the real numbers from running this
notebook, along with an explicit list of what those numbers do and don't
demonstrate — the recall measurement is real, but the dilution/accuracy
model is hand-picked, not fit to any real RAG system.

## 🧩 Why This Matters for AI Coding Systems

This experiment connects **retrieval design → downstream quality**:

- Corpus size → how much k you need for good recall
- k → both recall (up) and context dilution (also up)
- Net effect → an optimal k that isn't "as much as possible"

Modern RAG systems use this insight to:
- Cap top-k rather than maximize it
- Rerank before truncating context
- Trade off retrieval breadth against generation quality

## 🎓 Beginner Takeaway

> More retrieved context isn't automatically better.  
> Recall keeps climbing, but the model's ability to use what it retrieved
> doesn't climb forever with it.

Recall@k and downstream accuracy are two different curves — and RAG design
lives in the gap between them.
